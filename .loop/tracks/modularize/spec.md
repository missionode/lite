# Modularization migration

## Objective

Reduce update errors and maintenance cost by separating the monolithic application into explicit owners while preserving every current user flow, offline behavior, audio transition and protected sky visual.

## Acceptance criteria

- The atlas is the behavior and ownership reference before every extraction.
- One bounded subsystem moves per checkpoint behind a stable API.
- Touched source-slicing tests become direct behavior tests.
- Service-worker delivery includes every new runtime module.
- Journey order, storage keys, translations, audio timing, Earth atmosphere and Sun shield remain unchanged unless separately approved.
- Unrelated working-tree files are not modified or committed.
- After extraction parity is complete, measure startup and journey runtime before choosing lazy-loading boundaries. Keep a small startup core; cache optional feature modules for offline use without executing them until selected.
- Feature-level dynamic loading must preload on selection where useful, preserve offline/PWA starts, expose a safe unavailable-module path, avoid duplicate imports and retain current journey-start responsiveness.
- Optional workers, decoded buffers, AudioNodes, animation frames, observers and media sources receive explicit lifecycle/disposal contracts. Performance claims require before/after browser or device evidence.

## Exclusions

- No product redesign, new journey behavior or large one-pass rewrite.
- No browser or device-performance claim without matching evidence.
- No premature conversion of every small module into a separate request; loading boundaries follow measured cost and cohesive feature ownership.
- No push, merge or production publication without a separate request.
